# Social video publishing (Instagram Reels and Stories, LinkedIn video)
Videos become project media, are selected when publications are generated from a project, and are published by the existing Edge Function pipeline.
Branches: one per phase from updated main (`git switch -c <branch> --no-track origin/main`). Production migrations only with explicit user approval.

## Specs
- S1. User request: "Me han solicitado la opción de publicar videos en linkedin e instagram (aquí sería hacer reels e incluso histories)".
- S2. Videos belong to the project, not to the publication: "rompe la mecánica del proyecto de crear el contenido desde proyectos y de ahí generar publicaciones para redes sociales". The video is uploaded in the project, selected when publications are generated, and the publication configuration only chooses the format per network (Instagram: Reel or Story; LinkedIn: video).
- S3. Videos live in their own table and bucket in Supabase Storage, never inside `image_data`. A video lives while it stays in the project; deleting the video or the project removes the stored file.
- S4. Per-video limit (L24 supersedes L4): "los videos tendrán un tamaño máximo de 100mb y 5 minutos" -> 100000000 bytes and 300000 ms (minimums unchanged: 75000 bytes, 3 s). No per-plan quota for now; video size is stored so a quota can be added later.
- S5. "un solo video por publicación, esto no es un canal de youtube es para publicaciones en instagram y linkedin".
- S6. First delivery covers Instagram Reels, Instagram Stories and LinkedIn video. Out of scope: server-side transcoding, mixed photo/video carousels, music, stickers.
- S7. Validation happens in the browser before upload (format MP4/MOV, size, duration, aspect ratio) with clear Spanish messages; a poster frame is captured client-side and used as thumbnail so the dashboard does not load whole videos.
- S9. "Si, solo mp4 y limite de subida de 300mb": only MP4 (`video/mp4`, `.mp4`) is accepted; the size cap follows S4 (100 MB). Message for other formats: "Exporta el vídeo en MP4 (en iPhone: Ajustes → Cámara → Formatos → Más compatible)".
- S10. Video assignment (L15): "Se elige en cada publicación": generation stays as today; in the editor of each publication the user chooses "Sin vídeo" or one of the project's videos, so each publication may use a different video. "Sí, conserva ambas": a publication with a video keeps its photos; at publish time each network chooses its format (post/carousel with the photos, or Reel/Story/video with the video).
- S11. Images (L24): "en la creación de un proyecto subir el máximo de imágenes a 20 (ahora está en 10)"; the publication editor also allows 20 images (user choice "Subirlo también a 20"), matching the Instagram carousel and LinkedIn multi-image maximum of 20.
- S12. Roadmap (L24, not in the first delivery): "el video puede ir dentro del carrusel con las fotos (habiamos dicho que o video o carrusel)". Instagram carousels may mix photos and the video; LinkedIn cannot mix them in one post.
- S13. Story media (L33): "si seleciono una historia debería saber que imagen o que video voy a subir a la historia". Choice "Mostrar y poder elegir la imagen": for Historia (imagen) the user sees and chooses which selected photo is published (default: the first selected photo) without changing the carousel order; for Historia (vídeo) the UI shows the publication video that will be published. One story = one image or one video (Instagram API); story sequences are not requested ("No me importa que esté así").
- S8. Publishing never publishes twice: the existing irreversible-step protection applies to video; Instagram processing is polled across worker runs without blocking; LinkedIn upload is chunked without loading the whole video into memory.

## T1 contract (shared by the server and client writers)
- Table `public.project_videos`: `id uuid pk default gen_random_uuid()`, `project_id bigint not null references public.projects(id) on delete cascade`, `storage_path text not null unique` (`<project_id>/<id>.mp4`, must start with the row's project_id), `poster_path text null` (`<project_id>/<id>.jpg`), `original_name text not null` (1-255 chars), `bytes bigint not null` (75000-100000000 since L24), `duration_ms integer not null` (3000-300000 since L24), `width integer not null > 0`, `height integer not null > 0`, `faststart boolean not null` (moov atom before mdat), `position integer not null default 0`, `created_by uuid null default auth.uid()`, `created_at timestamptz not null default now()`. Index on `(project_id, position)`.
- RLS: select/insert/update/delete for `authenticated` when the caller is admin, project owner (`projects."user"`) or assigned editor (`projects.assigned`), through a new null-safe `private.project_media_allowed(p_project bigint)` helper. No anon access. Insert/update also require `storage_path` and `poster_path` to start with `<project_id>/`.
- Bucket `project-videos`: public (Instagram downloads `video_url` from a public URL), `file_size_limit 100000000` (L24), `allowed_mime_types ['video/mp4','image/jpeg']`. Storage policies insert/update/delete/select for `authenticated` through `private.project_video_path_allowed(name)`: name matches `^([1-9][0-9]{0,17})/[0-9a-f-]{36}\.(mp4|jpg)$` and the caller may edit that project. Direct SQL deletes on storage.objects are not allowed, so the client removes the objects (video and poster) before deleting the row, and `deleteProject` removes every object under `<projectId>/` in `project-videos` before deleting the project.
- Client upload: resumable TUS (`tus-js-client`) to `https://<ref>.storage.supabase.co/storage/v1/upload/resumable` (direct storage host), only `authorization: Bearer <access token>` (no apikey), chunk size 6 MB, `x-upsert: false`, progress shown; the client generates the uuid, uploads the video and the poster, then inserts the row; if the insert fails it removes the uploaded objects.
- Client validation before upload (blocking, Spanish messages): MP4 only (S9), size <= 100000000, duration 3 s-5 min (L24), readable metadata. Non-blocking: `faststart` false shows a warning that Instagram may reject the video. Poster: frame at ~1 s (or 0 for shorter videos) drawn to canvas, JPEG.

## T3 contract (shared by the three server writers)
- Formats: `publication_targets.format` in (`image`, `reel`, `story_image`, `story_video`, `video`). Instagram allows `image`, `reel`, `story_image`, `story_video`; LinkedIn allows `image`, `video`. `image` keeps today's behaviour byte for byte.
- `publication_targets.video_id uuid null references project_videos(id) on delete set null`: copied from `projectsPreview.video_id` when a target with `reel`, `story_video` or `video` is scheduled; scheduling such a target without a preview video fails. Schedule-time limits: `story_video` duration <= 60000 ms and bytes <= 100000000; `reel` and `video` use the project limits (3 s-5 min, <= 100000000 since L24).
- Types (`supabase/functions/_shared/social-publisher.ts`, pipeline writer owns it): `PublishFormat = "image" | "reel" | "story_image" | "story_video" | "video"`; `PublishTarget.format: PublishFormat`; `PublishVideo { url: string; posterUrl: string | null; bytes: number; durationMs: number; width: number; height: number; faststart: boolean }` (public URLs of bucket project-videos); `PublishPayload.video: PublishVideo | null`. For a video format with `video` null (video deleted after scheduling) the publisher returns `failed("validate", "action_required", "video_missing", ...)` before any network call.
- Payload RPC `publication_target_payload` returns `video` (same fields, snake or camel as the existing payload style, mapped in the store) for video formats, null otherwise. `story_image` uses the first published image of `images`.
- Cross-run processing: a publisher whose network is still processing media returns `failed("processing", "transient", "media_processing", ..., 60)` after checkpointing its ids; the pipeline must not count these polls as attempts and must give up after 60 minutes of processing (then `failed` with a clear code; safe because nothing was published).
- Instagram (Graph v27.0): `reel` -> container `media_type=REELS`, `video_url`, `caption`, `share_to_feed=true`, `cover_url` = poster when present; `story_video` -> `media_type=STORIES`, `video_url`; `story_image` -> `media_type=STORIES`, `image_url` (first image). Stories carry no caption. Status polled with `status_code` across runs (no in-run sleep loop longer than the remaining budget). `media_publish` stays the single irreversible step with the existing never-publish-twice rules.
- LinkedIn (`/rest`, LinkedIn-Version unchanged): `video` -> `POST /rest/videos?action=initializeUpload` (owner, fileSizeBytes, uploadCaptions false, uploadThumbnail true when a poster exists), PUT each 4194304-byte part read from the public video URL with an HTTP `Range` request (never the whole file in memory), collect ETags in order, upload the thumbnail, `POST /rest/videos?action=finalizeUpload`, poll `GET /rest/videos/{urn}` until `AVAILABLE` across runs, then `POST /rest/posts` with `content.media { id: <video urn>, title }`. Upload progress (upload token, video urn, instructions, ETags) is resumable across runs in table `public.publication_target_uploads (target_id uuid pk references publication_targets(id) on delete cascade, state jsonb not null, updated_at timestamptz)`, service_role only (RLS on, no policies, no grants to anon/authenticated), created by the pipeline writer and accessed by the LinkedIn writer from its own `_shared/social-upload-state.ts`.

## T7 contract (server and client writers)
- Column `publication_targets.story_image_url text null`: only for format `story_image`; the image_data `url` (sourceUrl, the original) of one published photo of the preview (status not `not_selected`). Readable by authenticated (add to the column SELECT grant).
- Entry function `publish-publication`: optional per-target `storyImageUrl` (string). Allowed only with `story_image` (else 422 `story_image_invalid`). Passed to `publication_targets_schedule`.
- `publication_targets_schedule` (replace from the LIVE definition in 20261122000100): for `story_image`, if `storyImageUrl` is given it must match a published photo of the preview (else `story_image_invalid`); if absent, store the first published photo; a preview with no published photo keeps today's error. Reschedule/replay keeps or updates the value consistently with how `format` is handled today.
- `publication_target_payload` (replace from the LIVE definition in 20261122000100): for `story_image`, `images` is exactly one element, the original of `story_image_url` if it is still a published photo of the preview; otherwise `images` is empty (the Instagram publisher already rejects a story_image without images; keep or map that to a clear code `story_image_missing`, action_required).
- Client: with format Historia (imagen) show the selected photos as small thumbnails and let the user choose one (default the first; keep the previous choice for scheduled targets from `story_image_url`); send `storyImageUrl`. With Historia (vídeo) show the video poster and name as "Vídeo de la historia". The Instagram vista preliminar for stories shows exactly the chosen image or the video. Texts in Spanish; `story_image_invalid` / `story_image_missing` mapped in the UI and in failure emails.
